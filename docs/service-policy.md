# 유료 파일럿 서비스 운영 정책 (승인 대기 초안)

> 상태: **DRAFT — 제품 소유자 승인 전에는 계약·SLA·운영 약속으로 사용하지 않는다.**
>
> 적용 대상: 국내 소규모 무역·유통업 고객 1개사의 첫 유료 파일럿
>
> 관련 결정: GitHub Issue #187, 개인정보·법률 검토는 #188, 실제 플랫폼 구성과 복원 증거는 #189

## 1. 권장안 요약

| 항목 | 권장값 |
|---|---|
| RPO | 최대 24시간 |
| RTO | 지원 시간 안에서 복구 개시 후 8 업무시간 |
| 지원 시간 | 평일 09:00~18:00 KST, 대한민국 공휴일 제외 |
| 지원 채널 | 전용 지원 이메일 또는 티켓 시스템 1개. P1 비상 연락 채널은 운영 담당자 지정 후 별도 제공 |
| 가용성 | 월 99.5% 내부 운영 목표(SLO). 파일럿 계약상 SLA·서비스 크레딧은 제공하지 않음 |
| 고객 데이터 반출 | 종료일 전후 요청 접수 후 10 업무일 이내 표준 형식으로 제공 |
| 데이터 파기 | 운영 데이터는 종료 또는 파기 요청 후 30일 이내, 백업 사본은 90일 이내 순환 삭제 |

RPO는 마지막 정상 백업 이후 허용 가능한 최대 데이터 손실 구간이고, RTO는 복구 작업을 시작한 뒤 업무 서비스를 다시 제공하기까지의 목표 시간이다. 지원 시간 밖에 접수된 장애의 응답·RTO 시계는 다음 지원 시간에 시작한다. 별도 24시간 지원 계약을 체결하지 않은 상태에서 24/7 대응을 약속하지 않는다.

## 2. 백업·복구 정책

### 백업 계층

1. Railway 네이티브 백업을 일간·주간·월간으로 동시에 구성한다.
   - 일간: 24시간마다, 6일 보존
   - 주간: 7일마다, 1개월 보존
   - 월간: 30일마다, 3개월 보존
2. 플랫폼 프로젝트 삭제·오조작에도 남도록 ERP와 Keycloak이 사용하는 PostgreSQL 전체를 매일 암호화된 논리 백업으로 별도 계정 또는 별도 저장소에 복제하고 30일 보존한다.
3. 백업 성공 여부를 매 업무일 확인하고 실패 시 P2로 처리한다. 마지막 정상 백업이 24시간을 넘기면 신규 배포와 고객 데이터 대량 변경을 중단한다.
4. 첫 고객 개통 전에 운영 백업을 격리 DB에 복원하고, 이후 분기마다 복원 훈련을 수행한다. 성공 기준은 [운영·복구 런북](operations-runbook.md)의 Flyway·테넌트·업무 모듈·Keycloak 데이터 대조와 로그인 후 핵심 조회 통과다.

Keycloak realm JSON 내보내기는 보조 설정 사본으로만 사용한다. Keycloak 공식 문서상 실행 중 내보내기의 일관성이 보장되지 않고 이벤트·지속 세션·폐기 토큰 등이 포함되지 않으므로 데이터베이스 백업을 복구 정본으로 삼는다.

### 복구 목표의 승인 조건

- RPO 24시간은 운영에서 매일 독립 백업이 성공한 증거가 있어야 유효하다.
- RTO 8 업무시간은 #189에서 실제 운영 규모 백업의 복원·검증 시간을 측정해 8시간 이내임을 입증해야 유효하다.
- 측정에 실패하면 출시를 막고, 용량·복원 절차·플랫폼 구성을 개선하거나 RTO를 계약 전에 다시 승인한다.

## 3. 지원·장애 대응

| 등급 | 기준 | 최초 응답 목표 | 고객 통지와 갱신 |
|---|---|---|---|
| P1 긴급 | 전체 로그인/서비스 불가, 테넌트 간 노출 가능성, 데이터 무결성 훼손, 중대한 보안 사고 | 지원 시간 내 1 업무시간 | 영향 확인 후 2 업무시간 이내 최초 통지, 복구까지 2시간마다 갱신 |
| P2 높음 | 핵심 업무 기능 불가 또는 심각한 성능 저하, 합리적 우회 방법 없음, 백업 실패 | 지원 시간 내 4 업무시간 | 같은 업무일에 통지, 상태 변경 또는 매 업무일 갱신 |
| P3 일반 | 일부 기능 오류, 우회 가능 문제, 사용 문의·개선 요청 | 2 업무일 | 지원 채널에서 처리 일정 안내 |

- 테넌트 간 노출 또는 보안 사고 가능성은 실제 유출 확정 전에도 P1로 분류한다.
- 법정 신고·정보주체 통지 여부와 시한은 #188의 법률 검토 결과를 우선한다.
- 장애 종료 후 5 업무일 이내 원인·영향·복구·재발 방지 조치를 기록하고, 고객 영향이 있었으면 비밀정보를 제외한 요약을 제공한다.
- 정기 점검은 일요일 02:00~04:00 KST를 기본 창으로 하며 48시간 전에 알린다. 긴급 보안 조치는 사전 통지 없이 수행할 수 있고 가능한 즉시 사후 통지한다.

## 4. 가용성 약속

- 첫 유료 파일럿의 월 가용성 **99.5%는 내부 운영 목표**이며 계약상 보장, 손해배상 또는 서비스 크레딧 기준이 아니다.
- 계획 점검, 고객 또는 고객 IdP·네트워크·단말 설정, 불가항력, 외부 플랫폼 장애는 가용성 산정에서 제외한다. 다만 외부 플랫폼 장애도 고객 통지와 복구 대응 대상이다.
- 계약상 SLA가 필요한 고객에게 판매하기 전에는 24/7 대응 인력과 플랫폼 제공자의 계약 SLA 또는 다중 리전 대체 구성을 확보하고 별도 가격·제외 조건·크레딧을 승인한다.

현재 권장 호스팅의 최소 등급은 Vercel Pro와 Railway Pro다. Vercel Hobby는 공식 약관상 개인·비상업 용도이므로 유료 고객 서비스에 사용하지 않는다. Railway Pro 지원은 통상 응답 안내일 뿐 SLO가 아니므로 Railway 응답 시간을 고객 SLA의 근거로 사용하지 않는다.

## 5. 계약 종료·데이터 반출·파기

1. 계약 종료 예정일을 알게 되면 고객에게 반출 요청 방법과 30일 보관 창을 안내한다.
2. 요청 접수 후 10 업무일 이내 CSV/JSON 등 기계 판독 가능한 표준 형식으로 고객 소유 업무 데이터를 제공한다. 첨부파일이 있으면 원본 파일과 목록을 함께 제공한다.
3. 운영 데이터와 계정은 계약 종료 또는 적법한 파기 요청 중 늦은 시점부터 30일 이내 삭제·비활성화한다.
4. 백업의 잔존 사본은 새 백업에 포함하지 않고 보존 주기에 따라 최대 90일 이내 순환 삭제한다. 복원 시 이미 파기 대상인 데이터가 되살아나지 않도록 재삭제 절차를 적용한다.
5. 법정 보존 의무, 분쟁 보존 또는 고객과의 별도 계약이 있으면 해당 범위만 격리·접근 제한하고 근거와 종료일을 기록한다.
6. 파기 완료 후 10 업무일 이내 대상·완료일·예외를 기록한 확인서를 제공한다.

전체 테넌트 반출 자동화와 파기 증거 생성은 현재 제품 기능으로 검증되지 않았다. 첫 고객 계약 전에 #189에서 실제 데이터 형식·첨부파일·복원 백업 재삭제 절차를 리허설해야 한다.

## 6. 플랫폼 근거와 한계

- [Railway Backups](https://docs.railway.com/volumes/backups): 일간 6일, 주간 1개월, 월간 3개월 보존과 동일 프로젝트·환경 내 복원 제약
- [Railway Support](https://docs.railway.com/platform/support): Pro의 통상 응답은 보장 SLO가 아니며 계약 SLA는 Enterprise에서 협의
- [Railway Logs](https://docs.railway.com/observability/logs): Pro 기본 로그 보존 30일
- [Vercel Pricing](https://vercel.com/pricing), [Vercel Terms](https://vercel.com/legal/terms): Hobby의 개인·비상업 제한과 Pro/Enterprise 차이
- [Keycloak Import and Export](https://www.keycloak.org/server/importExport): realm export의 백업 한계와 일관성 조건
- [Keycloak Production Configuration](https://www.keycloak.org/server/configuration-production): 운영 DB와 다중 인스턴스 가용성 권고

플랫폼 문서와 가격은 변경될 수 있다. #189 구성 시 최신 원문을 다시 확인하고, 실제 결제 플랜·지역·보존 설정을 운영 기록에 남긴다.
